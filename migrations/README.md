# PostgreSQL migrations

Files live in the repository root `migrations/` directory and are paired by version:

- `001_initial_schema.up.sql`: creates the complete schema after the consolidation.
- `001_initial_schema.down.sql`: removes it.
- `002_order_surcharge_discount.up.sql`: replaces the generic adjustment columns with explicit surcharge and discount amounts.
- `002_order_surcharge_discount.down.sql`: restores the generic adjustment columns as their net value.

The schema was consolidated from the former incremental migrations. A database created before the consolidation is already at the old version 5 and must be recreated or explicitly baselined before version 1 is applied; the migration runner will not replay it on such a database.

Run UP migrations in ascending order. Run DOWN migrations in reverse order. Use the migration runner selected by the project or execute each file with a PostgreSQL client against the intended database. Do not run migrations automatically during application startup.

## Identity columns

Every standalone surrogate primary key uses `BIGINT GENERATED BY DEFAULT AS IDENTITY`. `order_items` intentionally has no standalone identity: its composite primary key is `(order_id, item_id)` because one catalog item may occur only once per order.

## Important constraints

- Counter orders must be inserted as `CLOSED`.
- A table order may be `OPEN`, `AWAITING_PAYMENT`, `CLOSED`, or `CANCELED`.
- A closed order requires `closed_at` and `closed_by_user_id`.
- A canceled order requires `canceled_at` and `canceled_by_user_id`.
- Only one active table order may exist for a given `table_code` at a time (`OPEN` or `AWAITING_PAYMENT`).
- `order_items.quantity` must be positive.
- Unit prices, order totals, surcharges, and discounts are integer cents. Totals, surcharges, and discounts cannot be negative.
- A discount cannot exceed the subtotal plus the surcharge; the application enforces this because the subtotal is derived from the order lines.
- User and item removal is represented by `deleted_at`; historical foreign keys use restrictive deletion.
- Role codes are seeded as `ADMIN`, `CASHIER`, and `SERVER`.

## Indexes

Indexes exist only for query paths used by the application:

- Order history and filtered lists: `orders_history_idx`, `orders_status_created_idx`.
- Sales summary ranges: `orders_closed_at_idx`, `orders_canceled_at_idx`.
- Table occupancy: `orders_one_active_per_table_idx`.
- Payments by order and active refresh tokens per user.
- Sellable catalog by category and name.
- Audit log by time for operational inspection.

## Application responsibilities not expressible as simple constraints

The application must still enforce role permissions, state transitions, price snapshots, total recalculation, and transactional consistency. The SQL checks do not replace domain rules.

`orders.version` is available for optimistic concurrency control. The application may instead use row-level locking, but it must prevent lost updates.

`refresh_tokens` is included as a persistence foundation. Implement refresh-token flows only with an explicit rotation, expiry, and revocation policy.
